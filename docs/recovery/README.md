# Recovery Guide: Rebuilding Juniper Auto From Nothing But GitHub

This is the actual, executable procedure to go from "I have a Linux
machine and nothing else" to a fully validated Juniper Auto Phase 0
checkout. It assumes no prior knowledge of FLOWBOX and no leftover state
from any previous checkout -- if you can follow this on a machine that has
never seen this project before, Phase 0 has done its job (see
[project-governance](../research/project-governance.md), rule 38).

This exact procedure was executed as an isolated fresh-clone/fresh-venv
exercise (not a literal OS reinstall) during Phase 0 engineering; see
`docs/phases/phase-0-foundation.md` for the recorded result, and GitHub
Actions CI (`.github/workflows/phase-0-validation.yml`) for the equivalent
check on a genuinely separate clean Linux machine every time this repo is
pushed to.

## 1. Required OS assumptions

- A Linux distribution with a working `git`, `python3` (3.12.x), and
  `python3 -m venv` available. This was developed and validated on Ubuntu
  24.04-based Linux Mint 22.3 and on GitHub Actions' `ubuntu-latest`; any
  reasonably current Linux with Python 3.12 should work.
- No GPU is required for Phase 0. A CUDA-capable GPU (this project's
  consumer-hardware baseline is an NVIDIA RTX 2060, 6 GB VRAM) is used
  opportunistically if present, but every Phase 0 check also runs and
  passes with `device="cpu"` explicitly, and CI runs with no GPU at all.

## 2. Required system dependencies

- `git`
- `python3` version 3.12.x (see
  [environment specification](../architecture/environment-specification.md)
  for the canonical version)
- Internet access to `pypi.org` (for `pip install`) and `github.com`

No `uv`, no Poetry, no global `pip3`, and no pre-existing virtual
environment are required -- see
[ADR-0004](../adr/0004-dependency-locking-approach.md).

## 3. Clone

```bash
git clone https://github.com/Cinqic/Juniper-Auto.git
cd Juniper-Auto
```

## 4. Create the environment

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m ensurepip --upgrade
python -m pip install --upgrade pip
```

## 5. Install dependencies from the committed lock

```bash
pip install -r requirements-lock.txt
pip install -e . --no-deps
```

`requirements-lock.txt` is hash-pinned (`pip-compile --generate-hashes`);
`pip` will refuse to install if any downloaded package's hash doesn't match
what's recorded, which is the point.

## 6. Validate

```bash
python scripts/validate_repo.py --all
```

This runs, in order: environment sanity, imports, config validation,
parameter accounting, the frozen-artifact manifest check, the
time-accounting schema check, repository-integrity checks, artifact-hash
verification, the deterministic foundation probe, and the full pytest
suite. It exits non-zero and names the failing gate if anything is wrong.

## 7. Configuration locations

- `configs/architecture/ja150m-v0.1.yaml` -- frozen sparse architecture.
- `configs/architecture/ja150m-v0.1-dense.yaml` -- frozen dense control.
- Future training/runtime/tools/memory/evaluation configuration will live
  under the corresponding `configs/<domain>/` directory as those phases add
  it (see [ADR-0003](../adr/0003-configuration-format-and-validation.md)).

## 8. Manifest locations

- `manifests/frozen-artifacts.yaml` -- status of every named project
  artifact (architecture, tokenizer, datasets, checkpoints, etc.).
- `manifests/phase-0-artifact-hashes.yaml` -- SHA-256 hashes of the Phase 0
  artifacts listed in `juniper_auto/util/hashing.py`.

## 9. How future external artifacts will be restored

Phase 0 creates no external artifacts (no tokenizer, dataset, or
checkpoint exists yet -- see `manifests/frozen-artifacts.yaml`). When later
phases produce them, this section will document exactly where they are
hosted and how `scripts/validate_repo.py` (or its successor) fetches and
verifies them by hash. As of Phase 0: **there is nothing to restore beyond
this git repository.**

## 10. What is intentionally not stored in Git

See `.gitignore`. In particular: the `.venv/` virtual environment, Python
caches, any `.env`/secret files, downloaded/raw datasets, generated
datasets, transient logs, local checkpoints, and model weights. All of
these are either regenerated by this recovery procedure or (for datasets,
checkpoints) do not exist yet in Phase 0.

## 11. Troubleshooting known Phase 0 limitations

- **No standalone global `pip3` on some systems (e.g. this project's own
  FLOWBOX):** use `python3 -m venv .venv` and `python -m ensurepip
  --upgrade` inside it, as in Step 4 above, rather than relying on a system
  `pip3` binary.
- **`torch` install is large (multiple GB):** the committed lock file
  resolves `torch` without CPU/CUDA environment markers (see
  [ADR-0004](../adr/0004-dependency-locking-approach.md)), so the CUDA
  runtime libraries download even on a CPU-only machine. This is a known,
  accepted tradeoff, not a bug -- everything still runs correctly with
  `device="cpu"`.
- **`scripts/validate_repo.py --all` fails at "artifact hashes":** you (or
  a prior commit) changed one of the files listed in
  `juniper_auto/util/hashing.PHASE_0_HASHED_ARTIFACTS` without regenerating
  the manifest. Run `python scripts/hash_manifest.py` and commit the
  result.
- **CUDA/GPU determinism:** the seed framework
  (`juniper_auto/util/seed.py`) explicitly does not claim bitwise CUDA
  determinism -- only best-effort CPU determinism is asserted and tested.
  See `docs/phases/phase-0-sonnet-self-review.md` for this accepted
  limitation.
